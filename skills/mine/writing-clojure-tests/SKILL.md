# Writing Clojure Tests

## Writing Style

Write comments and test descriptions succinctly. Use Simplified Technical English.
Write docstrings succinctly.

## Development Sequence

Use Skill(clojure-repl-driven-development) to explore and implement one small
behavior at a time. Use the REPL to test ideas and inspect the running program.
After the behavior works, write automated tests that record it. The work is
complete when the tests record the behavior.

### Bug Reports

For a reported or suspected bug, first write a focused test that reproduces the
bug. Confirm that the test fails for the expected reason. Then use the REPL to
inspect the program and develop the fix. The work is complete when the regression
test and the relevant test suite pass.

## 1. Select the Test DSL

Before you change tests, inspect:

- project instructions and test documentation
- test and development dependencies
- behavior tests near the target and elsewhere in the repository
- template or generator sources when tests seem generated

A test DSL defines the test code. A test runner executes it. For example, Kaocha
runs `clojure.test` tests, including tests generated by Fulcro Spec. Kaocha
configuration identifies the runner, not the DSL.

Use the first matching row:

| Evidence                                                  | Select                                                                                     |
|-----------------------------------------------------------|--------------------------------------------------------------------------------------------|
| Project instructions specify a DSL                        | The specified DSL                                                                          |
| Behavior tests in the target module use one DSL           | The target module's DSL                                                                    |
| Behavior tests across the repository use one DSL          | The repository's DSL                                                                       |
| The repository uses multiple DSLs                         | The target module's DSL, then the most common repository DSL; ask if the result is unclear |
| No behavior tests exist, or only generated examples exist | Fulcro Spec                                                                                |

A behavior test verifies project behavior. A generated smoke test, sample
`deftest`, or placeholder assertion is an example, not an established DSL. When
you add the first behavior tests, delete these examples and use Fulcro Spec.

Before you change test code, select one DSL from project evidence.

## 2. Read the Framework Instructions

### Fulcro Spec

Read Skill(clojure-libraries/references/fulcro-spec.md) in full before you write or
change a Fulcro Spec test. For a new test suite:

1. Add Fulcro Spec with the project's test or development dependency method.
2. Confirm that the runner includes the test path.
3. Replace generated examples with behavior tests.

### `clojure.test`

Follow the project's existing `clojure.test` conventions.

### Other DSL

Follow the established DSL. Check Skill(clojure-libraries) for instructions. If
the index has no instructions, inspect the project's local documentation and the
dependency source before you change tests.

Before you continue, read the selected framework instructions. For a new suite,
list the required dependency and test-path changes.

## 3. Use Related Skills

Use each applicable skill:

- **Test code:** Use Skill(clojure-style-guide) for Clojure forms and namespace
  style. Use Skill(testing-anti-patterns) for assertions, mocks, and test-only
  production code.
- **REPL and test runs:** Use Skill(clojure-eval) for REPL work, namespace reloads,
  and focused test runs.
- **Kaocha:** Read Skill(clojure-libraries/references/kaocha).
- **Property-based tests:** Read
  Skill(clojure-libraries/references/test-check/overview).
- **Polylith workspaces:** Use Skill(clojure-polylith) for test locations and
  repository commands.
